# Review by C (round two)

Red-team review of designs A, B and D, v1. Checked against the [fact sheet](00-fact-sheet.md), the [stories](01-users-and-stories.md) and the 1.0.0 code in `custom_components/heads_up/hub/`. One code fact matters for all four designs, mine included: `_apply_deliver` in `engine.py` leaves out "a recipient that already has the message on that channel". A Deliver to the Admins adds nothing for an Admin the call itself already pushed to, so that Admin only ever gets the call's push, and if a hold made that push quiet, it stays quiet.

## Design A: two lanes and the "Always gets through" band

### Three most serious failures
1. Scenario 1 and S1 ("nights stay quiet for everything else"). Chris puts the tag `alarm` on the band. The band works per message, not per person, so every delivery of that message skips every hold, for every recipient. The leak automation also pushes to Anna and Ben (or the household audience), and at 03:00 they are all woken, not only the Admins who are meant to act. A Presence rule for speech is skipped too, so the leak is spoken into an empty house. A says "a message passes all holds or none" and lists this as given up, but it means S1 can only be met by editing every automation's audience.
2. Scenario 8 and S8. Chris wants the household speakers to speak when nobody was reached. In A the fallback is held like any delivery, so for an info message at night Night quiet keeps it quiet. A's only way to change that is the band, which works per message: to make the fallback speak, Chris has to put the message's tag on the band. Then that message's first push wakes everyone too. "If nobody was reached, speak, even at night" cannot be said without making the whole message loud. S8 asks for exactly this.
3. D-211 and D-213 in "all" mode. D-211 (decided) puts "Critical messages pass" in Which messages on every hold-back policy; A removes it and replaces it with a read-only line, which reopens a decided item without naming it. In "all" mode A changes behaviour: two reminders on one channel now run only the faster one. The way back given ("give each reminder its own channels") changes which channels get repeats, so it does not restore 1.0.0. Ben, who used two reminders as a "fast plus slow" pair, loses a repeat stream and has no exact way back.

### Idea worth stealing
Write the 1.0.0 "only the first" subtraction as plain "Not for" severities and tags wherever that is exact, and keep a link to another policy (`not_with`) only where it is not. Converted forms then read like ordinary forms. I take this into C v2.

## Design B: goals

### Three most serious failures
1. The four-language constraint and phone width. Each goal is a sentence with its blanks as buttons. Take German Pass on: "Wenn innerhalb von [30 Minuten] nachdem sie jemanden erreicht hat niemand auf [Warnungen] reagiert, [Admins] über [Push] informieren". The blanks come in a different order than in English, and the fields below keep the English order. At 380 px the sentence wraps across five lines of mixed buttons. Anna, who reads German, taps "[Warnungen]" and the focus jumps to a field that is not next to it. B names this as the biggest risk and gives a plain-text fallback, which means that in some languages the main idea of the design is gone.
2. Scenario 12 together with S1 (Chris's fear). After migration, critical messages pass because of one goal, "Critical messages get through", which lists the calm goals that had `critical_passes` on. Later, Anna adds a new Quiet times goal "Weekend lie-in" (wait until 10:00). B removed the per-policy "Critical messages pass", so nothing tells the new goal to let critical through. The migrated goal lists only the old goals, so a critical smoke alarm on Saturday 07:00 waits until 10:00. The form's preview only compares goals of the same kind, so it does not warn about this either. For a new "Gets through" goal B says it passes every calm goal, but the migrated one passes a list. These are two rules under one name.
3. Q4 ("one place per wish") and scenario 5. "Gets through ... and also push it to them" makes one goal both a strength and a send, so Chris has two places to change who gets the leak push: the Gets through goal and an Also send goal. In scenario 5 each rhythm has its own limit: with Urgent at most 12 and Hourly at most 6, after 7 urgent repeats X turns off, the hourly limit is already passed, and repeats stop. When X turns on again they start again. Ben cannot predict when the last reminder comes, which is the exact thing S5 asks the page to say.

### Idea worth stealing
Fill the same timeline from the ledger in each message's history: "Held until 07:00 by Night quiet; Leaks would have let it through, but it is off". This answers Q2, and Try a message alone does not. I take it, together with B's "Show details" switch that shows each card's switch entity ID for Ben.

## Design D: message types

### Three most serious failures
1. Scenario 11, the claim of no change. D assumes Away sits below the other four policies and "was never reached". The fact sheet's starting order is Summarize, Quiet hours, Away, Escalation, Reminder, Fallback, Deliver. So in a starter setup Away comes before Warning reminder and Critical delivery, and Away (all severities) takes every warning and critical message. The types D derives ("Critical delivery" as the default for critical, "Warning reminder" for warning) therefore add a push and repeats that 1.0.0 never sent. That breaks D-213 for the exact setup in scenario 11. The cell method could get this right, but the worked example shows that its output needs checking.
2. D-198 and D-213 with switches. In 1.0.0 "only the first", switching Night quiet off from an automation made the next matching policy (Away) act on info messages. D freezes the cells at migration, so after conversion that switch only removes quieting, and Away never takes over. Ben toggles policy switches from YAML, and the same toggle now gives different deliveries. In "all" mode one 1.0.0 policy becomes a section of several joined types, so one switch entity controls sections in many types. It is unclear what turning it off does, and the form cannot show it.
3. Q4 and scenario 8, plus a loud default. "Speak on the household speakers if nobody was reached" is one wish, set once per type (D names four). When Anna later adds the type Doorbell, she gets no fallback and is not told. "During quiet times" is set per type. The design does not say which choice a new type starts with. If it starts with "Send as usual", every new type wakes people at night: someone adds a type, and Chris's nights change. If it starts with "Send quietly", a new Alarm type is silent until somebody notices. Either way Chris's fear moves from the order to a default nobody sees. Separately, watch-rule messages always carry the tag `rule`, so a watch-rule leak that is a warning can only reach the Alarm type by being critical. That is pain point 6 again, for watch rules only (parity, rule 9).

### Idea worth stealing
"A window belongs to the day it starts" as the one sentence that settles scenario 2's Friday night, and the card note "No message gets this type unless a call names it" for converted policies that never act. Both go into C v2 (the note as "Never acts: ... (1.0.0)").
